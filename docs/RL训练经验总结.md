# RL训练经验总结

## 核心判断

基于当前整理出的两本全文集，一个最值得保留的判断是：

1. 环境设计决定“这个任务能不能被学出来”。
2. 奖励函数设计决定“模型最后学成什么东西”。

如果这两件事做错了，后面继续更换 PPO、SAC、TD3、GRPO，通常都只能带来有限改善。

## 一、环境设计经验

### 1. 先把真实问题翻译成一个“可学的 MDP”

环境设计最常见的误区，不是算法不够强，而是任务从一开始就没有被翻译成一个可学的问题。很多经验都在重复同一件事：先做一个最小可行环境，先让任务“能打通”，再逐步增加复杂度。环境一开始就做得过于复杂，agent 往往不是学不会，而是根本没有机会学。

### 2. 状态设计要“足够决策，但不过载”

状态空间里既不能缺信息，也不能塞太多冗余信息。

- 缺信息时，策略无法建立稳定映射，甚至会破坏马尔可夫性。
- 信息过多时，状态维度膨胀，训练容易变慢、发散或长期不收敛。

更稳的做法是：先用最小状态集把流程跑通，再逐步补充对决策真正有帮助的观测量。同时，状态通常应做归一化，否则不同量纲会直接影响网络优化。

### 3. 动作设计先服务于“可学性”，再服务于“最优性”

复杂连续动作虽然表达能力强，但探索难、训练慢、容易抖动。很多任务里，更稳的做法是先离散化动作，或者先把复杂动作拆成多个子动作，先验证环境和任务定义本身是对的，再切回连续动作做精细控制。

一句话说，动作空间先追求“能学”，再追求“学得优雅”。

### 4. 环境要稳定、可复现、可调试

一个训练环境如果 reset 不稳定、接口经常挂、运行效率低、长时间训练会积累错误，那么它就不适合作为 RL 主训练环境。比起“仿真越真实越好”，更重要的是：

- reset 逻辑可靠
- step / reset 接口语义清晰
- 训练吞吐足够高
- 日志和回放可观察
- bug 可以被快速定位

如果环境本身不稳定，再好的算法也只是在噪声上拟合。

### 5. 随机化要适度，而不是无差别加噪声

环境随机化的目标是提升泛化，不是制造混乱。更合理的做法是优先随机化那些真正影响泛化的因素：

- 初始状态
- 目标位置
- 障碍物分布
- 观测噪声
- 通信或执行延迟

而物理参数、基础动力学、动作响应等核心机制，不宜在初期训练中做过度扰动。环境随机化过强，训练会变得极不稳定；随机化过弱，又会导致策略只记住固定场景。

### 6. 仿真保真度是效率和迁移之间的权衡

高保真仿真更接近真实世界，但训练慢、调试重；低保真仿真训练快，但容易带来 sim-to-real gap。更务实的做法通常是分阶段：

- 早期用简化环境快速验证可学性
- 中期引入更真实的仿真细节
- 后期再做真实系统或高保真系统上的迁移与微调

## 二、奖励函数设计经验

### 1. 奖励必须和最终目标强对齐

奖励函数设计最重要的原则，不是“信号够不够多”，而是“优化方向对不对”。如果奖励只对应某个局部代理指标，而不是最终任务目标，agent 最终就会学到“高奖励但低价值”的策略。

很多失败案例的本质都不是训练不足，而是奖励错位。

### 2. 稀疏奖励和密集奖励要分层使用

真实目标最好保持干净、稳定、不可歪曲，比如：

- 最终任务是否完成
- 最终收益是否为正
- 最终答案是否通过验证

但仅靠最终奖励，很多任务又学不起来，因此训练初期通常需要加入适量中间反馈，例如：

- 距离目标是否更近
- 是否完成关键中间步骤
- 是否满足必要格式或结构要求

最稳的做法不是完全依赖 dense reward，也不是死守 sparse reward，而是：

- 用稀疏奖励定义真正目标
- 用密集奖励帮助探索
- 控制中间奖励强度，避免盖过主目标

### 3. 奖励塑形必须警惕“刷中间分”

奖励塑形最常见的问题，不是没效果，而是效果太“好”，好到 agent 学会钻空子。例如为了拿“接近目标”的奖励，agent 学会原地打转；为了拿格式分，模型开始输出表面合规但内容空洞的答案。

因此在设计 shaping reward 时，要一直追问两个问题：

1. 这个中间奖励是否真的在帮助最终目标？
2. 它会不会改变最优策略本身？

如果能使用 potential-based shaping，通常更稳，因为它更容易保证不改变原任务最优解。

### 4. 奖励项不要堆得过于复杂

奖励项过多时，系统会很难调，权重之间相互干扰，最后往往谁都没学好。很多复杂任务的更优策略不是把所有期望行为都写成 reward，而是把一部分内容变成：

- 环境约束
- 动作约束
- 终止条件
- 可验证规则

能显式约束的内容，尽量不要全塞进 reward 里做软惩罚。

### 5. 奖励必须防 exploit 和 reward hacking

agent 一旦发现某种“高分捷径”，就会不断利用它。高 reward 不等于高质量行为，因此奖励函数必须主动防作弊。高频经验包括：

- 不要只看 reward 曲线，要看行为回放
- 不要只看训练效果，要看最终目标指标
- 不要只看局部奖励，要检查总 reward 与最终任务结果的相关性

一旦发现“reward 在涨，但最终效果没有涨”，优先怀疑奖励函数，而不是先怀疑算法。

### 6. 惩罚项要有明确语义

惩罚项不是越多越好，而是要足够明确地表达“不允许什么”。一些经验显示：

- 对安全边界、资源限制、风险控制这类问题，惩罚通常是必要的
- 线性惩罚有时过于温和，无法建立边界感
- 指数式或分段式惩罚更容易让 agent 感知危险区域

但惩罚过大又会让策略过度保守，所以惩罚应服务于约束，而不是替代目标本身。

### 7. 奖励要尽量可验证、可复现、可诊断

能写成 verifier 的任务，通常比依赖主观评分的任务更稳。能程序判定对错、能规则化复现、能拆分评分来源的奖励，更适合长期迭代，也更适合大规模训练。

如果任务天然不可完全验证，也应尽量拆成多个更可验证的子维度，而不是完全依赖单一模糊评分。

## 三、最有价值的实践原则

把两本内容里的反复共识压缩下来，最有价值的实践原则大概是下面几条：

- 环境先保证“可学”，奖励再保证“学对”。
- 先做最小可行环境，不要一开始就做满配复杂系统。
- 状态只保留决策真正需要的信息，并统一归一化。
- 动作空间先为探索和收敛服务，再为精细控制服务。
- 真实目标用稀疏奖励锚定，探索过程用适量密集奖励引导。
- 中间奖励只能辅助主目标，不能喧宾夺主。
- 约束优先写进环境或规则，少靠 reward 软惩罚硬撑。
- 不只看 reward 曲线，要同时看行为回放和最终任务指标。
- 每次只改一个环境因素或一个奖励组件，否则无法定位问题。
- 找到最优 checkpoint 就停，不要默认“训得更久一定更好”。

## 四、一套可直接落地的工作流

如果要把这些经验转成实际开发流程，可以按下面顺序推进：

1. 先定义最小任务闭环，只保留必要状态、动作和终止条件。
2. 用随机策略、规则策略或手动交互验证环境的状态转移和奖励计算。
3. 先写一个干净的最终目标奖励，再补最少量的中间引导。
4. 每次只新增一个环境复杂因素或一个奖励组件，单独观察影响。
5. 同时记录训练 reward、行为回放、最终任务指标三类日志。
6. 一旦发现“高 reward 低效果”，优先检查奖励错位和 exploit。
7. 能写成程序验证的部分，优先改成 verifier 或规则奖励。
8. 用验证集或测试场景监控泛化，及时 early stopping。

## 五、总结

最终可以把这些经验压缩成一句话：

环境设计解决的是“能不能学出来”，奖励函数设计解决的是“最后会学成什么”。前者决定收敛，后者决定对齐。真正稳定的 RL 训练，不是靠不断换算法，而是靠把环境和奖励先打磨正确。
