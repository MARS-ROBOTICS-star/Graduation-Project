# Stage1 低维地形特征观测与奖励优化方案

本文整理 MGDP 启发下的 Stage1 优化方案，并结合当前 `complete_car` 代码中的实际高度 patch、观测拼接和奖励函数实现给出可落地的修改路线。

这份方案的定位是：下一轮 Stage1 训练前的观测与奖励结构优化设计。它不是对 MGDP 的完整复刻，也不是已经完成的实验结论。

2026-05-07 落地状态：第一阶段观测结构已实现并通过 `1` iteration headless smoke。当前 Stage1 actor 维度为 `82`，critic 维度为 `660`；`terrain-gated reward` 仍按本文档规划留到第二阶段，不在本次实现中同时修改。

## 1. 总体结论

当前最合理的优化方向是：

```text
局部高度 patch D_patch
        │
        ├── 完整 flatten(D_patch) ───────────────→ critic privileged obs
        │
        └── 确定性几何特征提取 f_geo(D_patch)
                    │
                    └── z_terrain ─────────────→ actor obs
```

也就是：

- actor 不再直接输入完整 34×17 高度 patch，而是输入低维、可解释的地形几何特征 `z_terrain`。
- critic 保留完整高度 patch，作为训练时的 privileged information。
- reward 不直接奖励“识别出某类地形”，而是用确定性地形 gate 调节速度、姿态、接触支撑和冲击约束。
- 第一版不引入复杂 CNN / world model / depth reconstruction。先做确定性几何特征，保证可解释、易调试、适合毕设论文表述。

这个方向和 MGDP 的核心思想一致：actor 使用低维地形表征降低学习难度，critic 使用更完整的特权信息稳定价值估计。但本项目不需要复刻 MGDP 的复杂视觉模型、memory、map decoder 或 contrastive loss。

## 2. 当前 Stage1 的实际实现状态

### 2.1 当前高度 patch

当前 Stage1 配置在 `complete_car_stage1_cfg.py` 中启用了高度测量：

```python
self.terrain.measure_heights = True
self.terrain.patch_front_extent = 0.942209
self.terrain.patch_rear_extent = 0.942209
self.terrain.patch_preview_length = 1.0
self.terrain.patch_rear_margin = 0.40
self.terrain.patch_half_width = 0.280374
self.terrain.patch_side_margin = 0.5
self.terrain.patch_resolution_x = 0.10
self.terrain.patch_resolution_y = 0.10
```

由 `terrain_cfg.py` 的 `_get_measured_points_x()` 和 `_get_measured_points_y()` 可得：

```text
x_min = -(patch_rear_extent + patch_rear_margin) = -1.342209
x_max = patch_front_extent + patch_preview_length = 1.942209
y_min = -(patch_half_width + patch_side_margin) = -0.780374
y_max = patch_half_width + patch_side_margin = 0.780374
```

当前 patch 维度为：

```text
x 方向 34 个采样点
y 方向 17 个采样点
总高度点数 = 34 × 17 = 578
```

需要特别注意：`env.py` 的 `_compute_critic_height_patch()` 当前返回的不是地形高度本身，而是：

```python
relative_height = root_pos_w[:, 2:3] - terrain_height
```

因此当前观测中的 patch 更准确地说是：

```text
D_patch = root_z - terrain_z
```

它表示车体参考高度到地形表面的竖直距离。前方地形越高，`D_patch` 反而越小；前方坑或下台阶越深，`D_patch` 反而越大。

所以后续提取几何特征时，必须先转换为以局部支撑面为零点的相对地形高度：

$$
H_{rel} = D_{ref} - D_{patch}
$$

其中 `D_ref` 可以取中车附近小区域的均值或中位数。这样：

- `H_rel > 0` 表示前方地形比当前支撑面高，对应上台阶 / 障碍。
- `H_rel < 0` 表示前方地形比当前支撑面低，对应下台阶 / 坑 / gap。

如果跳过这一步，`step_up_height` 和 `drop_depth` 的符号会被反过来，actor 会学到错误地形语义。

### 2.2 当前 actor / critic 观测

当前 `observations.py` 中，actor 观测已从“基础观测 + 完整高度 patch”改为“基础观测 + 低维地形特征”。actor 观测由以下分量拼接：

| 分量 | 维度 |
|---|---:|
| `ball_joint_pos` | 6 |
| `ball_joint_vel` | 6 |
| `base_lin_vel` | 3 |
| `base_ang_vel` | 3 |
| `wheel_joint_vel` | 6 |
| `wheel_longitudinal_slip` | 6 |
| `wheel_slip_angle` | 6 |
| `wheel_normal_contact_force` | 6 |
| `relative_goal_commands` | 4 |
| `last_actions` | 8 |
| `terrain_features` | 28 |

基础观测维度为：

```text
6 + 6 + 3 + 3 + 6 + 6 + 6 + 6 + 4 + 8 = 54
```

当前总 actor 观测维度为：

```text
54 + 28 = 82
```

critic 观测由 actor 观测继续拼接完整高度 patch 得到：

```python
def compute_critic_observation(actor_obs: torch.Tensor, height_patch: torch.Tensor | None = None) -> torch.Tensor:
    terms = [_finite_tensor(actor_obs)]
    if height_patch is not None:
        terms.append(_finite_tensor(height_patch))
    return _finite_tensor(torch.cat(terms, dim=-1))
```

也就是说，当前实现中 actor 和 critic 已经形成信息分工：

```text
actor_obs  = 54 维基础观测 + 28 维 z_terrain
critic_obs = actor_obs + 578 维完整高度 patch
```

当前维度为：

```text
actor_obs_dim = 82
critic_obs_dim = 82 + 578 = 660
```

因此，第一阶段观测结构已经完成：actor 不直接面对 578 维原始 patch，critic 保留完整高度 patch 作为 privileged information。第二阶段优化重点不再是观测拼接，而是把已有确定性 `TerrainGate/*` 接入速度命令、reward、reset 和 curriculum。

### 2.3 当前奖励函数

当前 `rewards.py` 的奖励项为：

```python
REWARD_TERM_NAMES = (
    "distance_to_target",
    "progress_to_target",
    "reached_target",
    "far_from_target",
    "angle_diff",
    "turn_speed_penalty",
    "slip_penalty",
    "action_rate_penalty",
    "contact_support_penalty",
    "edge_speed_penalty",
)
```

Stage1 中主要权重为：

| 奖励项 | 当前 Stage1 权重 / 参数 | 作用 |
|---|---:|---|
| `distance_to_target_weight` | 6.0 | 鼓励靠近目标点 |
| `progress_to_target_weight` | 8.0 | 鼓励每步向目标推进 |
| `reached_target_base_reward` | 2.0 | 到达 waypoint 的基础奖励 |
| `reached_target_weight` | 6.0 | 放大到达 waypoint 奖励 |
| `far_from_target_weight` | -2.0 | 偏离目标过远惩罚 |
| `angle_diff_weight` | 6.0 | 鼓励朝向目标方向 |
| `turn_speed_penalty_weight` | 0.0 | 当前关闭 |
| `slip_penalty_weight` | -2.0 | 惩罚纵向滑移和滑移角 |
| `action_rate_penalty_weight` | -10.0 | 惩罚动作突变 |
| `contact_support_penalty_weight` | -4.0 | 惩罚前/中/后三模块支撑不足 |
| `edge_speed_penalty_weight` | -6.0 | 前方地形突变时惩罚高速通过 |

当前已有几个值得保留的机制：

- `progress_to_target` 已经被 `progress_gate` 调制。纵向滑移和滑移角越大，正向推进奖励放大越弱。
- `slip_penalty` 使用接触权重 mask，不会把完全离地轮子的滑移无限放大。
- `contact_support_penalty` 按前、中、后三个模块检查支撑，和三车体结构相关。
- `edge_speed_penalty` 已经利用 patch 中前方高度突变强度 `edge_strength` 限制地形边缘前的速度。

当前不足也比较明确：

- `edge_strength` 只看高度突变绝对值，不区分上台阶、下台阶、坑、粗糙地形和离散障碍。
- `contact_support_penalty` 对不同地形使用同一套支撑逻辑，台阶或坑上短暂前/后轮离地可能被过度惩罚。
- reward 还没有明确表达“上台阶时前车适度抬头”“下台阶时避免前车俯冲”“左右轮高差时保持横滚稳定”等行为。
- actor 输入完整 patch，但 reward 只通过一个 `edge_strength` 使用 patch 信息，观测语义和奖励约束之间还没有形成清晰闭环。

## 3. 核心问题诊断

当前 Stage1 的主要问题不是“小车完全看不到地形”，而是：

```text
小车看到了原始高度 patch，但 actor 需要自己从 578 个点里学出可行动的地形语义。
```

对三车体六轮主动铰接车而言，真正和控制相关的不是每一个高度采样点，而是：

- 前方是否有上台阶；
- 上台阶高度是多少；
- 台阶边缘离车多远；
- 前方是否有下台阶、坑或 gap；
- 左右轮路径是否存在高度差；
- 前、中、后三车体下方支撑面是否连续；
- 当前是否需要减速、抬前车、保持中后车支撑或控制横滚。

如果 actor 直接吃完整 patch，PPO 需要同时完成“地形几何理解”和“运动控制学习”。这会降低样本效率，也会导致一些现象：

- 推进能力上升，但动作饱和、滑移、俯仰冲击仍偏高。
- 台阶上看似能走，但容易在半途 timeout 或 reset。
- 策略能偶尔到较高 row，但不能稳定保持并继续推进。
- 粗糙地形、上下坡可能先可用，台阶和离散障碍仍成为瓶颈。

因此，下一轮优化应把高度 patch 先转成低维、可解释、直接对应控制含义的 `z_terrain`。

### 4.1 actor 观测

建议 Stage1 actor 改为：

```text
actor_obs =

  ball_joint_pos,
  ball_joint_vel,
  base_lin_vel,
  base_ang_vel,
  wheel_joint_vel,
  wheel_longitudinal_slip,
  wheel_slip_angle,
  wheel_normal_contact_force,
  relative_goal_commands,
  last_actions,
  z_terrain
]
```

也就是：

```text
actor_obs_dim = 54 + terrain_feature_dim
```

第一版 `terrain_feature_dim` 固定采用 28 维，则 actor 维度为：

```text
54 + 28 = 82
```

这比当前 632 维 actor 输入小很多，同时语义更明确。

### 4.2 critic 观测

建议 Stage1 critic 改为：

```text
critic_obs =
[
  actor_obs,
  flatten(D_patch),
  optional_privileged_contact_or_body_state
]
```

第一版可以先采用：

```text
critic_obs = actor_obs + flatten(D_patch)
```

若 `terrain_feature_dim = 28`，则 critic 维度为：

```text
82 + 578 = 660
```

这会形成明确的信息分工：

- actor 学习低维地形语义下的可执行控制。
- critic 看到完整 patch，帮助价值函数更准确评估复杂地形上的长期收益。

注意：当前 actor 已经包含 `wheel_longitudinal_slip`、`wheel_slip_angle` 和 `wheel_normal_contact_force`，这些量某种意义上已经是接触特权信息。如果后续面向真机可迁移性，需要重新讨论哪些量允许 actor 使用，哪些量只能放入 critic。本方案当前先服务于 Stage1 训练稳定性，不把这个问题伪装成已经解决的迁移结论。

## 5. 低维地形特征设计

### 5.1 patch 预处理

当前原始 patch 为 `D_patch = root_z - terrain_z`。建议特征提取器内部统一转换：

```python
D = D_patch.view(num_envs, nx, ny)  # 当前 nx=34, ny=17
D_ref = D[:, center_x_mask, center_y_mask].median(dim=...).values
H_rel = D_ref - D
H_norm = torch.clamp(H_rel / h_scale, -1.0, 1.0)
```

其中：

- `D_ref` 取中车附近区域，表示当前局部支撑面参考。
- `H_rel` 才是后续用于理解上台阶、下台阶和左右高差的相对地形高度。
- `h_scale` 第一版可取 0.25 m。该值不代表物理上最大高度，只是把高度特征压到适合网络学习的范围。

### 5.2 建议的物理区域划分

当前 patch 的局部坐标含义是：

- `x`：车体 yaw 对齐坐标下的前后方向。
- `y`：车体 yaw 对齐坐标下的左右方向。

建议不要在代码里只写死索引，而是根据 x/y 坐标生成 mask。第一版可以采用：

| 区域 | 建议局部范围 | 用途 |
|---|---|---|
| rear support | `-0.94 <= x < -0.30` | 后车体支撑地形 |
| middle support | `-0.30 <= x <= 0.30` | 中车体当前支撑地形 |
| front support | `0.30 < x <= 0.94` | 前车体支撑地形 |
| front preview | `0.94 < x <= 1.94` | 车头前方预瞄地形 |
| center track | `abs(y) <= 0.20` | 中线纵向剖面 |
| left/right track | `abs(y)` 接近轮距区域 | 左右轮路径高度差 |

本轮 `play.py` 回放中已通过红色局部 `+Y` 半区箭头确认：当前 patch 局部坐标的 `+Y` 位于车体左侧。因此第一版实现固定采用：

```text
left_track = y_points > 0
right_track = y_points < 0
left_right_height_diff = left_track_height_mean - right_track_height_mean
```

其中 `left_right_height_diff > 0` 表示左轮路径预瞄区域平均地形高度高于右轮路径，后续 `roll_demand` 的符号也应按这个约定设计和验证。

### 5.3 第一版地形特征列表

建议第一版 `z_terrain` 固定使用 28 维。下面给出一组可直接实现的特征。

#### A. 前方纵向地形特征

| 特征 | 含义 |
|---|---|
| `h_front_mean` | 前方预瞄区域平均高度 |
| `h_front_max` | 前方最高障碍高度 |
| `h_front_min` | 前方最低下陷深度 |
| `front_slope` | 前方整体坡度 |
| `front_roughness` | 前方高度标准差 |
| `step_up_height` | 中线剖面最大正高度突变 |
| `drop_depth` | 中线剖面最大负高度突变 |
| `step_up_distance` | 最近上台阶边缘距离 |
| `drop_distance` | 最近下台阶 / 坑边缘距离 |
| `gap_width` | 连续负高度区域的纵向宽度 |

其中中线剖面可定义为：

```text
profile(x) = median_y H_rel(x, y), y in center_track
```

然后：

```text
d_profile(i) = profile(i + 1) - profile(i)
step_up_height = max(max(d_profile), 0)
drop_depth = max(max(-d_profile), 0)
```

#### B. 左右轮路径特征

| 特征 | 含义 |
|---|---|
| `left_track_height_mean` | 左轮路径平均高度 |
| `right_track_height_mean` | 右轮路径平均高度 |
| `left_track_step_height` | 左轮路径最大上台阶高度 |
| `right_track_step_height` | 右轮路径最大上台阶高度 |
| `left_track_drop_depth` | 左轮路径最大下陷深度 |
| `right_track_drop_depth` | 右轮路径最大下陷深度 |
| `left_right_height_diff` | 左右轮路径平均高度差 |
| `roll_demand` | 由左右高度差估计出的横滚补偿需求 |

这些特征对应横滚稳定和左右轮附着差异。它们比完整 patch 更直接告诉 actor：是否需要提前用主动铰接进行横滚调姿。

#### C. 三车体支撑区域特征

| 特征 | 含义 |
|---|---|
| `front_support_height` | 前车体下方地形平均高度 |
| `middle_support_height` | 中车体下方地形平均高度 |
| `rear_support_height` | 后车体下方地形平均高度 |
| `front_middle_height_diff` | 前车体与中车体支撑高度差 |
| `middle_rear_height_diff` | 中车体与后车体支撑高度差 |
| `support_height_std` | 三车体支撑高度不均匀程度 |
| `pitch_demand_front` | 前车相对中车的俯仰补偿需求 |
| `pitch_demand_rear` | 后车相对中车的俯仰补偿需求 |

这些特征直接对应三车体主动铰接控制问题：

- 前车是否应该抬头；
- 中车是否正在进入高差区域；
- 后车是否应该跟随抬升；
- 下台阶时前车是否需要避免俯冲。

#### D. 连续地形 gate

建议不要使用硬 one-hot 地形分类，而是使用连续 gate：

| 特征 | 含义 |
|---|---|
| `g_step_up` | 当前前方更像上台阶 / 上障碍 |
| `g_step_down` | 当前前方更像下台阶 |
| `g_gap` | 当前前方更像坑 / gap |
| `g_rough` | 当前前方更像粗糙地形 |
| `g_flat` | 当前前方更接近平地 |

示例：

$$
g_{step\_up} = sigmoid((step\_up\_height - h_{thr}) / \sigma)
$$

$$
g_{gap} = sigmoid((drop\_depth - d_{thr}) / \sigma)
$$

$$
g_{flat} = 1 - clamp(g_{step\_up} + g_{step\_down} + g_{gap} + g_{rough}, 0, 1)
$$

第一版阈值可以和当前 `edge_speed_penalty` 的经验范围对齐：

- `h_thr` 可从 0.04～0.10 m 之间开始。
- `d_thr` 可从 0.04～0.10 m 之间开始。
- `rough_thr` 可参考粗糙地形高度范围 0.01～0.04 m。

## 6. 与当前奖励函数的配合方式

### 6.1 保留现有推进主干

当前奖励中的推进主干应保留：

- `distance_to_target`
- `progress_to_target`
- `reached_target`
- `far_from_target`
- `angle_diff`

原因是 Stage1 的任务仍然是跨地形 waypoint 推进。低维地形特征的目的不是改变任务目标，而是让 actor 更容易根据地形选择合适动作。

当前 `progress_to_target` 已经通过滑移 gate 抑制“高滑移硬顶式推进”。这个思路应保留，因为它能避免策略只靠轮子空转换取短期位移。

### 6.2 用地形 gate 改造 edge speed

当前 `edge_speed_penalty` 只基于 `edge_strength` 限制前方高度突变时的速度：

```text
edge_strength = normalize(max_abs_height_jump)
edge_safe_speed = flat_speed_limit - edge_strength * (flat_speed_limit - edge_speed_limit)
```

建议改为使用更明确的地形 gate：

$$
g_{edge} = max(g_{step\_up}, g_{step\_down}, g_{gap})
$$

$$
v_{safe} = v_{flat} - g_{edge}(v_{flat} - v_{edge})
$$

这样仍然保持当前 `edge_speed_penalty` 的功能，但含义更清楚：

- 上台阶前减速；
- 下台阶 / gap 前减速；
- 平地和普通粗糙地形不无谓限制速度。

### 6.3 增加上台阶前车姿态 gate

当 `g_step_up` 较高时，reward 应鼓励前车适度抬头，而不是靠轮子高速撞台阶。

建议形式：

$$
\theta_{front}^{ref} = clamp(k_h \cdot step\_up\_height, 0, \theta_{max}) \cdot g_{step\_up}
$$

$$
r_{front\_pitch} = g_{step\_up} \cdot exp(-(\theta_{front} - \theta_{front}^{ref})^2 / \sigma_{\theta}^2)
$$

注意这里奖励的是“运动行为”，不是“识别出台阶”。`g_step_up` 只是控制该姿态奖励何时生效。

### 6.4 增加下台阶 / gap 防俯冲 gate

当 `g_step_down` 或 `g_gap` 较高时，前车直接俯冲会带来大 pitch 冲击和接触丢失。建议添加轻量 anti-dive 约束：

$$
g_{drop} = max(g_{step\_down}, g_{gap})
$$

$$
r_{anti\_dive} = g_{drop} \cdot exp(-(\theta_{front} - \theta_{safe})^2 / \sigma_{\theta}^2)
$$

其中 `theta_safe` 不一定是明显抬头，也可以是接近 0 或轻微上仰。关键是避免前车在下台阶边缘大角度俯冲。

### 6.5 改造 contact support 逻辑

当前 `contact_support_penalty` 对前、中、后三模块统一要求最小支撑：

```python
front_support = max(front_left, front_right)
mid_support = max(mid_left, mid_right)
rear_support = max(rear_left, rear_right)
```

这在平地、坡地、粗糙地形上合理，但在台阶 / gap 上需要更细：

- 平地 / 粗糙地形：鼓励前、中、后三模块都有稳定支撑。
- 上台阶：允许前轮短暂接触变化，但不允许中车长期失去支撑。
- 下台阶 / gap：允许前车短暂离地或接触弱化，但中后车支撑应更稳定。

建议把支撑惩罚改为 gate 组合：

$$
p_{contact} = g_{flat}p_{all\_module} + g_{step\_up}p_{mid\_rear} + g_{drop}p_{middle}
$$

这能避免策略在台阶上为了满足“所有模块都接触”而出现不自然硬顶，也能防止它完全放弃中车支撑。

### 6.6 保持 reward 的解释边界

reward 不应直接依赖 learned terrain token，也不应奖励“这是台阶”这个判断本身。更合理的逻辑是：

```text
确定性地形特征判断当前地形状态
        ↓
gate 决定哪些运动质量约束更重要
        ↓
reward 奖励真实运动行为：推进、低滑移、姿态平稳、接触合理、动作平滑
```

这比把地形分类结果直接当奖励目标更容易解释，也更适合论文写作。

## 8. 代码框架草案

下面是第一版确定性特征提取器的结构草案。实际实现时应使用 `cfg.terrain._get_measured_points_x()` 和 `_get_measured_points_y()` 生成 mask。

```python
def compute_terrain_features(cfg, height_patch: torch.Tensor):
    num_envs = height_patch.shape[0]
    x_points = torch.as_tensor(cfg.terrain._get_measured_points_x(), device=height_patch.device, dtype=height_patch.dtype)
    y_points = torch.as_tensor(cfg.terrain._get_measured_points_y(), device=height_patch.device, dtype=height_patch.dtype)

    nx = x_points.numel()
    ny = y_points.numel()
    d_patch = height_patch.view(num_envs, nx, ny)

    center_x = (x_points >= -0.30) & (x_points <= 0.30)
    center_y = torch.abs(y_points) <= 0.20
    d_ref = d_patch[:, center_x][:, :, center_y].median(dim=2).values.median(dim=1).values.view(num_envs, 1, 1)

    # 当前 patch 是 root_z - terrain_z，所以这里转成“地形相对高度”。
    h_rel = d_ref - d_patch
    h_scale = 0.25
    h_norm = torch.clamp(h_rel / h_scale, -1.0, 1.0)

    front_preview = x_points > float(cfg.terrain.patch_front_extent)
    center_track = torch.abs(y_points) <= 0.20
    # 回放可视化已确认局部 +Y 对应车体左侧。
    left_track = (y_points >= 0.15) & (y_points <= 0.45)
    right_track = (y_points <= -0.15) & (y_points >= -0.45)

    front = h_norm[:, front_preview]
    profile = h_norm[:, :, center_track].median(dim=2).values
    d_profile = profile[:, 1:] - profile[:, :-1]

    step_up_height = torch.relu(d_profile).max(dim=1).values
    drop_depth = torch.relu(-d_profile).max(dim=1).values
    h_front_mean = front.mean(dim=(1, 2))
    h_front_max = front.amax(dim=(1, 2))
    h_front_min = front.amin(dim=(1, 2))
    front_roughness = front.std(dim=(1, 2))

    left_profile = h_norm[:, :, left_track].mean(dim=2)
    right_profile = h_norm[:, :, right_track].mean(dim=2)
    left_right_height_diff = left_profile[:, front_preview].mean(dim=1) - right_profile[:, front_preview].mean(dim=1)

    rear_mask = (x_points >= -0.94) & (x_points < -0.30)
    mid_mask = (x_points >= -0.30) & (x_points <= 0.30)
    front_mask = (x_points > 0.30) & (x_points <= 0.94)

    rear_support = h_norm[:, rear_mask].mean(dim=(1, 2))
    mid_support = h_norm[:, mid_mask].mean(dim=(1, 2))
    front_support = h_norm[:, front_mask].mean(dim=(1, 2))

    front_mid_diff = front_support - mid_support
    mid_rear_diff = mid_support - rear_support
    support_std = torch.stack((front_support, mid_support, rear_support), dim=1).std(dim=1)

    sigma = 0.1
    step_thr = 0.08 / h_scale
    drop_thr = 0.08 / h_scale
    rough_thr = 0.03 / h_scale
    g_step_up = torch.sigmoid((step_up_height - step_thr) / sigma)
    g_drop = torch.sigmoid((drop_depth - drop_thr) / sigma)
    g_rough = torch.sigmoid((front_roughness - rough_thr) / sigma)
    g_flat = 1.0 - torch.clamp(g_step_up + g_drop + g_rough, 0.0, 1.0)

    terrain_features = torch.stack(
        (
            h_front_mean,
            h_front_max,
            h_front_min,
            step_up_height,
            drop_depth,
            front_roughness,
            left_right_height_diff,
            front_support,
            mid_support,
            rear_support,
            front_mid_diff,
            mid_rear_diff,
            support_std,
            g_step_up,
            g_drop,
            g_rough,
            g_flat,
        ),
        dim=1,
    )

    diagnostics = {
        "step_up_height": step_up_height,
        "drop_depth": drop_depth,
        "front_roughness": front_roughness,
        "left_right_height_diff": left_right_height_diff,
        "support_std": support_std,
        "g_step_up": g_step_up,
        "g_drop": g_drop,
        "g_rough": g_rough,
        "g_flat": g_flat,
    }
    return torch.nan_to_num(terrain_features), diagnostics
```

这段代码只是结构草案。正式实现时需要补齐：

- `step_up_distance`
- `drop_distance`
- `gap_width`
- `front_slope`
- `left/right_track_step_height`
- `left/right_track_drop_depth`
- `pitch_demand_front`
- `pitch_demand_rear`
- `roll_demand`

## 9. 全链路验证标准

### 9.1 单元级验证

需要构造几类人工 patch：

## 10. 论文表述边界

当前方案可以支持的表述：

- 本项目借鉴 MGDP 中 actor 使用低维地形表征、critic 使用 privileged terrain information 的思想。
- 针对三车体六轮主动铰接车，设计了确定性局部地形几何特征，用于表达上台阶、下台阶、左右轮高差和三车体支撑变化。
- 该方案旨在降低 actor 直接解析完整高度 patch 的学习难度，并提高 reward 与地形语义之间的可解释性。

当前不能直接声称：

- 主动铰接结构已经被证明优于其他结构。
- 低维地形特征一定优于完整高度图输入。
- 该策略已经具备真机可迁移能力。
- MGDP 的复杂感知模型已被本项目等价复现。

这些结论都需要后续消融实验、回放观察和多地形指标共同支持。

但是 `complete_car_cfg.py` 里要注意 history：当前 `history_length=1`，未来若打开 history，`actor_obs` 是已经 history 展平后的张量。因此推荐在 `__post_init__()` 中显式计算：

```python
actor_step_obs_dim = total_dim(build_observation_descriptor(self))
actor_obs_dim = (
    actor_step_obs_dim * self.observations.history_length
    if self.observations.use_history and self.observations.history_length > 1
    else actor_step_obs_dim
)
critic_obs_dim = actor_obs_dim
if self.terrain.measure_heights:
    critic_obs_dim += self.terrain.get_num_height_points()
```

这样 critic 的含义就是：

```text
critic_obs = actor_obs_after_history + current full height patch
```

第一版 Stage1 维度应为：

```text
actor_step_obs_dim = 54 + 28 = 82
actor_obs_dim = 82
critic_obs_dim = 82 + 578 = 660
```

### 12.5 observation 拼接修改

当前 `observations.py` 的 `compute_actor_observation_from_raw_terms()` 接收 `height_patch` 并直接 append。需要改为接收 `terrain_features`：

```python
def compute_actor_observation_from_raw_terms(
    cfg,
    raw_terms: dict[str, torch.Tensor],
    terrain_features: torch.Tensor | None = None,
) -> torch.Tensor:
    ...
    if terrain_features is not None:
        terms.append(_finite_tensor(terrain_features))
    return _finite_tensor(torch.cat(terms, dim=-1))
```

critic 改为：

```python
def compute_critic_observation(
    actor_obs: torch.Tensor,
    height_patch: torch.Tensor | None = None,
) -> torch.Tensor:
    terms = [_finite_tensor(actor_obs)]
    if height_patch is not None:
        terms.append(_finite_tensor(height_patch))
    return _finite_tensor(torch.cat(terms, dim=-1))
```

`env.py` 的 `_get_observations()` 对应改为：

```python
terrain_height_patch = self._compute_critic_height_patch()

    self.cfg,

    terrain_features,

actor_obs = update_history(self._obs_history, current_actor_obs)
critic_obs = compute_critic_observation(actor_obs, terrain_height_patch)
return {"actor": actor_obs, "critic": critic_obs}
```

同时在 `__init__()` 中初始化：

```python
self._last_terrain_features: torch.Tensor | None = None
self._last_terrain_feature_diagnostics: dict[str, torch.Tensor] = {}
```

### 12.13 第二阶段 reward 接入位置

当第一阶段确认 actor/critic 观测结构能稳定训练后，再接入 terrain-gated reward。

#### 12.13.1 `edge_speed_penalty`

当前 `_compute_edge_preview()` 仍可以保留用于 diagnostics，但 reward 中的 edge gate 建议改为：

$$
g_{edge} = max(g_{step\_up}, g_{step\_down}, g_{gap})
$$

并继续复用当前安全速度逻辑：

$$
v_{safe} = v_{flat} - g_{edge}(v_{flat} - v_{edge})
$$

这样 `edge_speed_penalty` 的含义从“任意高度突变减速”变为“台阶、下台阶、gap 前减速”。

#### 12.13.2 前车姿态和防俯冲

在 `assets/robot_cfg.py` 增加：

```python

    "body_car_chassis",
    "head_car_chassis",
    "tail_car_chassis",
]
```

在 `env.py` 初始化时：

```python

```

如果 IsaacLab 找不到 `head_car_chassis` 或 `tail_car_chassis`，说明 USD body 名称和预期不一致，应先用已有 asset 检查脚本确认实际 body 名，不要在 reward 中猜。

reward 所需姿态：

```python

middle_pitch = module_rpy[:, 0, 1]
front_pitch = module_rpy[:, 1, 1]
rear_pitch = module_rpy[:, 2, 1]
```

新增 reward component 建议：

```text

anti_dive
```

权重第一版保持轻量，避免姿态项压过推进主任务：

```python

anti_dive_weight = 1.0
front_pitch_max_ref_rad = 0.25
front_pitch_sigma_rad = 0.20
anti_dive_safe_pitch_rad = 0.0
```

#### 12.13.3 gate-aware contact support

当前 `contact_support_penalty` 对三模块统一处理。第二阶段建议改为：

$$
g_{drop} = max(g_{step\_down}, g_{gap})
$$

$$
p_{contact} =
\frac{
g_{flat}p_{all} + g_{rough}p_{all} + g_{step\_up}p_{mid\_rear} + g_{drop}p_{middle}
}{
g_{flat} + g_{rough} + g_{step\_up} + g_{drop} + \epsilon
}
$$

其中：

- `p_all`：前/中/后三模块支撑不足惩罚。
- `p_mid_rear`：中车和后车支撑不足惩罚。
- `p_middle`：中车支撑不足惩罚。

这会让台阶和 gap 上的短暂前轮接触变化更合理，同时保留中车支撑约束。

## 13. 第二阶段 terrain-gated reward / control / reset 落地方案

本节对应 2026-05-08 的下一轮优化：第一阶段低维地形特征观测已经落地，`525` iteration 测试表明平地能力基本保留，但台阶和离散障碍仍是瓶颈；运动质量上仍有较高 `contact_loss_rate`、`longitudinal_slip_abs_mean`、`pitch_abs_mean` 和 `action_saturation_rate`。因此第二阶段不再继续扩大 actor 观测，而是把现有确定性 `TerrainGate/*` 接入控制链路、reward、reset 和日志。

### 13.1 当前真实代码链路

当前 Stage1 动作和底层控制链路是：

```text
policy actions, shape = [num_envs, 8]
        │
        ├── actions[:, 0:2]
        │       ↓
        │   map_base_actions_to_planar_command()
        │       ↓
        │   planar_command = [vx_cmd, yaw_rate_cmd]
        │
        └── actions[:, 2:8]
                ↓
            map_ball_joint_actions_to_desired_positions()
                ↓
            desired_ball_joint_targets

planar_command + desired_ball_joint_targets + contact force
        ↓
TorchWheelSpeedAllocator.compute_low_slip_control_targets()
        ↓
shaped_planar_command, wheel_speed_reference, wheel_torque_targets, ball_joint_position_targets
```

关键入口：

| 文件 | 当前职责 | 第二阶段需要改什么 |
|---|---|---|
| `base/env.py` | action 预处理、height patch、terrain feature、reward 调用、done/reset、Stage1Eval 日志 | 在 wheel allocator 之前加入 terrain-gated `vx` 硬限速；维护 stuck buffer；把 terrain gates 和新诊断量传给 reward / metrics |
| `mdp/terrain_features.py` | 从 `D_patch` 提取 28 维 `z_terrain` 和 `g_step_up`、`g_step_down`、`g_gap`、`g_rough`、`g_flat` | 保持第一版不变；第二阶段直接复用 diagnostics 里的 gate 和 `step_up_distance_norm` / `drop_distance_norm` |
| `mdp/rewards.py` | 计算 reward component 和 reward diagnostics | 增加 terrain-aware edge speed、gate-aware contact、stuck、airborne spin、action soft limit；姿态项等符号确认后再接入 |
| `base/complete_car_cfg.py` | 共享参数字段 | 增加新 reward / control / stuck 参数字段，Stage0 默认权重保持 `0.0` |
| `baseline/complete_car_stage1_cfg.py` | Stage1 显式参数主入口 | 设置第二阶段 Stage1 默认权重和安全速度 |
| `mdp/terminations.py` 或 `base/env.py` | done term 计算 | 新增 `stuck_timeout` 终止项，Stage1 专用 |
| `mdp/stage1_eval.py` | 全局和分地形评价指标 | 增加 stuck、pitch rate、下落速度、速度门控激活率等指标 |
| `rsl_rl/utils/logger.py` | TensorBoard 和终端日志过滤 | 允许写入新增 `Debug/Stage1/*` 和 `Stage1Eval/*` 指标 |

PPO 主框架不需要为本轮 reward 改造而重写。当前 `obs_groups = {"actor": ["actor"], "critic": ["critic"]}` 已支持 actor / critic 不同维度；`RolloutStorage` 和 PPO 也已经支持 Stage1 最高 row retired 后的 `train_mask`。

### 13.2 本轮核心假设

当前失败不是“actor 完全不知道台阶存在”，因为 actor 已经输入 28 维确定性地形特征。更合理的假设是：

```text
policy 已经看到台阶 / 下台阶 / gap 的低维特征
        ↓
但 reward 和控制链路仍主要鼓励尽快向目标推进
        ↓
台阶上“冲一下、顶一下、卡一下”的收益仍可能高于“减速、调姿、稳定支撑”的收益
```

所以第二阶段必须同时改四件事：

1. 控制链路：台阶 / gap 前真实限制 `vx_cmd`，而不是只在 reward 里扣分。
2. reward：让推进收益和运动质量约束的量级接近，避免质量项太小。
3. reset/curriculum：卡住不能无限拖到 timeout，也不能卡住后仍被当作高 row 可继续练习。
4. 日志：新增 gate、生效速度、姿态、stuck 和接触支撑分项，否则训练后无法判断修改是否真的起作用。

### 13.3 保留任务推进主干

Stage1 的主任务仍是沿 terrain column 推进到下一 row target，因此以下主干不删除：

```text
distance_to_target
progress_to_target
reached_target
far_from_target
angle_diff
```

全地形 Stage1 默认仍保持：

```python
progress_to_target_weight = 8.0
reached_target_weight = 6.0
```

用户已确认：不建立单独的 `Stage1b` 台阶 / 障碍专训配置。因此第二阶段仍沿用全地形 Stage1 主线，不临时降低 `progress_to_target_weight` 和 `reached_target_weight`，也不默认启用质量门控 progress。

质量门控 progress 只作为后续备选研究点保留，不进入下一轮实现：

$$
quality\_multiplier = 0.4 + 0.6 \cdot clamp(quality\_score, 0, 1)
$$

$$
effective\_progress = progress\_to\_target \cdot quality\_multiplier
$$

这样做的含义是：运动质量很差时仍然允许一点推进奖励，避免策略完全不动；但硬冲、严重滑移、严重接触丢失时，推进收益会明显缩水。

当前执行口径：全地形 Stage1 继续同时覆盖平地、坡地、粗糙地形、上下台阶和离散障碍；本轮只改变 terrain-gated 运动质量约束，不改变地形采样任务结构。

### 13.4 A1：terrain-gated edge speed + 硬速度门控

当前 `edge_speed_penalty` 只在 reward 里惩罚超速，而且使用的是 `_compute_edge_preview()` 的高度突变强度。525 run 里 `desired_planar_vx_raw` 和 `shaped_planar_vx_raw` 没有明显下降，说明只靠 reward 软惩罚不足以让策略真正台阶前减速。

第二阶段第一步改为：

```text
TerrainGate/g_step_up
TerrainGate/g_step_down
TerrainGate/g_gap
        ↓
计算不同硬地形的安全速度
        ↓
在 wheel allocator 之前直接限制正向 vx_cmd
        ↓
reward 再惩罚 raw command 和实际速度超出安全速度
```

建议安全速度：

| 参数 | 建议初值 | 含义 |
|---|---:|---|
| `terrain_speed_step_up_mps` | `0.50` | 上台阶前最高正向速度 |
| `terrain_speed_step_down_mps` | `0.35` | 下台阶前最高正向速度 |
| `terrain_speed_gap_mps` | `0.40` | gap / 离散障碍前最高正向速度 |

计算方式：

$$
v_{safe}^{up} = v_{flat} - g_{step\_up}(v_{flat} - v_{up})
$$

$$
v_{safe}^{down} = v_{flat} - g_{step\_down}(v_{flat} - v_{down})
$$

$$
v_{safe}^{gap} = v_{flat} - g_{gap}(v_{flat} - v_{gap})
$$

$$
v_{safe} = min(v_{safe}^{up}, v_{safe}^{down}, v_{safe}^{gap})
$$

在 `env.py::_pre_physics_step()` 中，插入位置必须在：

```python
planar_command = mdp_actions.map_base_actions_to_planar_command(...)
```

之后、`compute_low_slip_control_targets(...)` 之前。

建议实现：

```python
vx_cmd_raw = planar_command[:, 0].clone()
vx_forward = torch.clamp(vx_cmd_raw, min=0.0)
vx_reverse = torch.clamp(vx_cmd_raw, max=0.0)
vx_forward_limited = torch.minimum(vx_forward, v_safe)
planar_command[:, 0] = vx_forward_limited + vx_reverse
```

这样只限制向前冲台阶，不禁止倒车脱困。

新增 reward：

$$
P_{edge\_speed} =
g_{edge}
\left(
relu(vx_{raw} - v_{safe})^2
+ 0.5 \cdot relu(vx_{actual} - v_{safe})^2
\right)
$$

其中：

$$
g_{edge} = max(g_{step\_up}, g_{step\_down}, g_{gap})
$$

第一版 `terrain_aware_edge_speed_penalty_weight` 建议设为 `-2.0` 到 `-5.0`，但最终以 TensorBoard 中实际 component 量级校准，目标是后期：

```text
Reward/terrain_aware_edge_speed_penalty ≈ -0.002 到 -0.008
```

### 13.5 A2：gate-aware contact support

当前 `contact_support_penalty` 用统一逻辑处理所有地形：

```text
front_support = max(head_left, head_right)
mid_support   = max(body_left, body_right)
rear_support  = max(tail_left, tail_right)
```

当前轮索引约定来自 `WHEEL_JOINT_NAMES`：

| 模块 | wheel indices |
|---|---|
| 中车 body | `0, 1` |
| 前车 head | `2, 3` |
| 后车 tail | `4, 5` |

这个逻辑适合平地、坡地和粗糙地形，但台阶 / gap 上不应强制前、中、后三模块同等接触。第二阶段改成 gate-aware contact：

$$
g_{support\_all} = max(g_{flat}, g_{rough})
$$

$$
g_{drop} = max(g_{step\_down}, g_{gap})
$$

$$
w_{all}, w_{up}, w_{drop}
=
\frac{g_{support\_all}, g_{step\_up}, g_{drop}}
{g_{support\_all} + g_{step\_up} + g_{drop} + \epsilon}
$$

三个支撑惩罚：

```text
P_all_module:
  front / mid / rear 都不能长期支撑不足

P_up_support:
  上台阶时重点保证 mid + rear 支撑，front 可短暂变化

P_drop_support:
  下台阶 / gap 时重点保证 mid + rear 支撑，front 落地冲击由 anti-dive 管
```

组合：

$$
P_{contact}
= w_{all}P_{all\_module}
+ w_{up}P_{up\_support}
+ w_{drop}P_{drop\_support}
$$

同时加轻量左右支撑差异项，避免 `max(left, right)` 掩盖单侧失撑：

$$
P_{lr\_balance}
= g_{edge}(0.2b_{front} + 0.5b_{mid} + 0.3b_{rear})
$$

其中 `b_front = abs(front_left - front_right)`，中车权重更高，因为中车是当前简化模型的主要参考体。

建议保留现有 `contact_support_penalty_weight = -4.0` 的量级，但删除 `/ max_episode_length` 后必须重新校准；目标是后期：

```text
Reward/contact_support_penalty ≈ -0.002 到 -0.008
```

```text

Debug/Stage1/ContactSupport/w_drop
Debug/Stage1/ContactSupport/front_support
Debug/Stage1/ContactSupport/mid_support
```

### 13.6 A3：上台阶姿态与下台阶 anti-dive

用户已人工确认球铰 pitch 符号：

```text
spm1_platform_joint_y > 0 时，前车体低头。
spm2_platform_joint_y > 0 时，后车体抬头。
```

因此，如果第一版姿态 reward 直接使用关节角：

```text
前车体抬头目标：spm1_platform_joint_y 应为负值。
后车体抬头目标：spm2_platform_joint_y 应为正值。
```

这是下一轮实现必须遵守的符号约定；不能再按“正 pitch 等于抬头”的通用直觉写 reward。

推荐姿态信号优先级：

1. `spm1_platform_joint_y` 和 `spm2_platform_joint_y` 的实际关节角。
2. 前车体相对中车体 pitch、后车体相对中车体 pitch。
3. 不使用 root pitch 作为主要姿态 reward，因为 root pitch 在坡地和台阶里混入整车地形姿态。

上台阶姿态不是正奖励刷分，而是阶段性 penalty：

$$
theta_{front\_ref}
= - clamp(k_h h_{step\_up}, 0, theta_{max}) \cdot g_{step\_up}
$$

$$
P_{step\_up\_posture}
= approach\_mask \cdot g_{step\_up}
\left(\frac{theta_{front} - theta_{front\_ref}}{sigma_{theta}}\right)^2
$$

`approach_mask` 建议：

```text
0.2 m < edge_distance_front < 1.2 m
goal_rel_x > 0.5 m
```

也就是：只有真的接近上台阶边缘、目标仍在前方时，才要求前车适度准备姿态。车已经顶到台阶上后，不应一直奖励大抬头。

这里的负号来自人工确认结果：`spm1_platform_joint_y < 0` 才表示前车体抬头。若后续改用“前车体相对中车体 pitch”而不是关节角，则必须重新核对该相对 pitch 的正负号，不能直接复用关节角符号。

下台阶 / gap 的 anti-dive 不写成“永远抬头”，而是限制俯冲、角速度和垂向下落：

$$
P_{anti\_dive}
= g_{drop}
\left[
0.5\left(\frac{theta_{front} - theta_{safe}}{sigma_{theta}}\right)^2
+ 0.2\left(\frac{pitch\_rate}{sigma_{pitch\_rate}}\right)^2
+ 0.5\left(\frac{v_{z\_down}}{sigma_{vz}}\right)^2
\right]
$$

其中 `v_z_down = relu(-root_lin_vel_w[:, 2])`。如果暂时没有前车体 pitch rate，可第一版用 `root_com_ang_vel_b[:, 1]` 作为诊断和近似，但文档和论文中必须说明它是近似量，不等同于前车局部 pitch rate。

建议参数：

| 参数 | 建议初值 |
|---|---:|
| `step_up_front_posture_penalty_weight` | `-0.3` 到 `-1.0` |
| `drop_anti_dive_penalty_weight` | `-1.0` 到 `-3.0` |
| `front_pitch_max_ref_rad` | `0.25` |
| `front_pitch_sigma_rad` | `0.20` |
| `drop_pitch_rate_sigma_radps` | `1.0` |
| `drop_vz_down_sigma_mps` | `0.5` |

### 13.7 A4：stuck penalty / stuck reset

离散障碍和上台阶常见失败是卡住不动。只靠 timeout 太慢，且会把“卡住 40 秒”混成普通超时样本。

在 `env.py` 新增：

```python
self._stage1_stuck_time = torch.zeros(self.num_envs, device=self.device)
```

每步根据 terrain gate、速度和目标位置更新：

```python
hard_gate = torch.maximum(g_step_up, torch.maximum(g_step_down, g_gap))
low_forward_speed = v_forward < 0.05
target_still_ahead = goal_rel_x > 0.5
stuck_now = (hard_gate > 0.3) & low_forward_speed & target_still_ahead
self._stage1_stuck_time = torch.where(
    stuck_now,
    self._stage1_stuck_time + self.step_dt,
    torch.zeros_like(self._stage1_stuck_time),
)
```

reward：

```text
stuck_time > 1.0 s 后开始扣分
```

done：

```text
stuck_time > 10.0 s 触发 stuck_timeout
```

`stuck_timeout` 应作为 Stage1 terminal done term，不并入普通 `time_out`。reset curriculum 中：

```text
stuck_timeout -> move_down
```

用户已确认：`stuck_timeout_s = 10.0 s` 后直接退级。这样比 `2.0 s` 更宽松，能给策略留出低速调整、倒车脱困或重新接触的时间；但如果 10 秒仍无有效推进，就说明当前 row 对策略过难，应退一级重新练。

### 13.8 空转轮、动作软限幅和球铰软限位

这三项不作为 A1 的第一优先级，但建议写好参数和日志接口。

空转轮惩罚：

$$
P_{airborne\_spin}
= mean((1 - c_i) \cdot |omega_i|)
$$

其中 `c_i` 是当前底层接触权重，`omega_i` 是轮关节速度。权重建议 `-0.005` 到 `-0.05`。该项用于避免离地轮高速空转后落地硬顶台阶。

动作软限幅：

$$
P_{action\_soft\_limit}
= mean(relu(|a| - 0.8)^2)
$$

权重建议 `-0.2` 到 `-0.8`。它不是禁止大动作，而是不鼓励长期把动作顶到接近 `1.0`。

球铰软限位：

$$
P_{ball\_joint\_soft\_limit}
= mean(relu(q_{usage} - 0.85)^2)
$$

用户已确认：球铰软限位第一版只记录日志，不进入 reward。因此下一轮实现不新增 `ball_joint_soft_limit_penalty` reward component，只保留分地形 `ball_joint_limit_usage_max` 诊断，用于判断后续是否有必要讨论。

### 13.12 通俗解释：采用后 reward 会变成什么效果

旧 reward 更像是在对小车说：

```text
你要尽快往目标点走。
滑一点、动作猛一点、接触差一点会扣分，
但扣得不一定足够大。
看到台阶前方有突变时会扣超速分，
但不会真正拦住你的速度命令。
```

所以策略可能学到：

```text
先冲过去，能过就赚推进奖励；
过不去就靠轮子打滑、球铰大动作硬顶；
即使姿态冲击和接触质量不好，推进收益仍可能更划算。
```

新方案更像是在给小车加一套按地形变化的驾驶规则：

```text
平地 / 坡地 / 粗糙地形：
    允许正常推进，但仍要求低滑移、动作平稳、模块有支撑。

上台阶前：
    先限速；
    前车体要准备合理姿态；
    中车和后车要保持支撑；
    轮子不能靠大滑移硬顶。

下台阶 / gap 前：
    速度更低；
    前车体不能猛俯冲；
    垂向下落速度和 pitch rate 要小；
    中后车不能失去支撑。

离散障碍 / 卡住：
    原地不动不会被当作“耐心训练”；
    卡住超过一定时间会扣分并 reset / 退级。

动作输出：
    不是禁止大动作；
    但长期接近饱和会被扣分，鼓励策略用更有余量的球铰动作。
```

最重要的变化是：reward 不再只是“能往前就好”，而是“在当前地形条件下，用合理速度、合理姿态、合理支撑往前”。这会让早期训练的 row 推进速度可能变慢，但如果设计有效，后期应看到：

- 台阶前 `vx_actual` 下降。
- 台阶上下 `pitch_abs_mean`、`pitch_rate_abs_mean`、`vz_down_mean` 下降。
- `contact_loss_rate` 下降。
- `longitudinal_slip_abs_mean` 和 `action_saturation_rate` 下降。
- `row_advance_rate` 不只是偶尔上升，而是在运动质量改善后稳定上升。

这仍然不能证明主动铰接结构优于其他结构，只能说明：在当前 Stage1 任务、当前三车体六轮小车模型、当前地形 curriculum 和 reward 设计下，策略是否从“硬冲推进”转向了更健康的地形条件化通过行为。
